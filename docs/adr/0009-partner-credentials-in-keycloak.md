# ADR-0009: Partner credentials in Keycloak and the gateway; no secrets in our database

- Status: Proposed
- Date: 2026-10-11
- Scope: Module 1

## Context

UC-01.05 issues, rotates and revokes OAuth client credentials, mTLS
certificates, IP allow-lists, scopes, rate limits and webhook signing keys,
per partner and environment. Secrets must never be stored in clear or logged
(NFR-UP01-S06). Credential operations must be automated by API, never done
by hand in a console (NFR-UP01-I02). Revocation must take effect within 60 s.

## Decision

1. **Keycloak** holds partner OAuth clients (client-credentials grant) and
   enforces scopes. **Spring Cloud Gateway** enforces mTLS (certificate
   fingerprint bound to the client), IP allow-lists and per-partner rate
   limits (Redis-backed).
2. Module 1's `ApiClient` aggregate stores only **metadata**: client ID,
   environment, scopes, rate limits, certificate fingerprint and expiry, IP
   list, webhook URL, signing-key ID, status and history. It never stores a
   secret.
3. Client secrets are generated by Keycloak and delivered through a one-time
   link (Vault response wrapping) that expires after first view or 72 hours.
   Webhook signing keys are generated and held in Vault; the webhook service
   (Module 13) signs with them by key ID.
4. All Keycloak and gateway operations go through a `CredentialProvider`
   adapter, so a bank that standardises on a different IdP or gateway can
   plug in its own implementation.
5. Revocation and restriction (UC-01.07) update Keycloak and publish a priority
   event that the gateway consumes (ADR-0007).

## Alternatives considered

- **Store hashed secrets in our own database and validate in the gateway.**
  We would be re-implementing an identity provider.
- **API keys only.** These do not meet the OAuth 2.0 plus mTLS requirement
  (NFR-UP01-S07).

## Consequences

- Sandbox and production use separate Keycloak realms (or installations), so
  credentials can never be shared across environments.
- Open question Q8: Northern Arc's and South Indian Bank's current IdP and
  gateway decide which `CredentialProvider` implementation we build first.
